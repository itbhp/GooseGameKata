AGENTS
======

Purpose
-------
This file tells automated agents how to build, test, lint, and edit Java code in this repository so they can continue work reliably and consistently.

Project layout & tools
----------------------
- Maven project at repository root (`pom.xml`). Use the Maven wrapper where possible: `./mvnw` (UNIX) or `mvnw.cmd` (Windows).
- Sources: `src/main/java` and tests: `src/test/java` (standard Maven layout).
- Test reports: `target/surefire-reports/` (generated by Surefire).

Quick commands (run in repository root)
-------------------------------------
Build the project (full):

```
./mvnw clean package
# or
mvn clean package
```

Run all tests:

```
./mvnw test
# or
mvn test
```

Run a single test class (example):

```
./mvnw -Dtest=MineGooseGameTest test
# or fully-qualified if needed
./mvnw -Dtest=it.twinsbrain.dojos.MineGooseGameTest test
```

Run a single test method (example):

```
./mvnw -Dtest=MineGooseGameTest#shouldDoSomething test
# exact method name required
```

Surefire pattern notes
----------------------
- The Maven Surefire `-Dtest=` supports patterns; simple class names usually work for this repository's layout. If you hit ambiguous matches, use the fully-qualified class name.
- Reports: `target/surefire-reports/` contains XML and plain text outputs useful for CI.

Linting and formatting
----------------------
- No project-wide formatter or linter config is present in the repo by default (no `.editorconfig`, no Google Java Format config, no Checkstyle config discovered). Agents must avoid committing formatting tool configs without approval.
- Recommended (manual) checks agents may run locally or in CI (add plugins if maintainers approve):
  - Checkstyle: `mvn checkstyle:check` (requires adding plugin/config to `pom.xml`).
  - PMD: `mvn pmd:check` (requires plugin/config).
  - SpotBugs: `mvn com.github.spotbugs:spotbugs-maven-plugin:check`.
  - google-java-format (standalone):

```
java -jar /path/to/google-java-format.jar -i $(find src -name '*.java')
```

- Prefer using the Maven wrapper (`./mvnw`) in CI to ensure consistent Maven version.
- If you propose adding a linter/formatter to `pom.xml`, include a brief rationale and tests that the configuration doesn't break the build before committing.

Code style guidelines (for automated agents)
-------------------------------------------
Follow these conventions when editing Java code in this repository. They are intentionally pragmatic so another agent or human can read and maintain code easily.

- Formatting
  - Keep code formatted with an automated formatter when possible. If no formatter is enforced, follow Oracle/Google-like defaults: 4-space indent, braces on same line, 100-120 char wraps.
- Imports
  - Use explicit imports (no wildcard imports). Let IDEs/formatters manage reordering; if editing by hand, group imports by standard -> third-party -> project and keep unused imports removed.
- Typing & nulls
  - Use primitive types for primitives where appropriate (`int`, `boolean`).
  - Avoid returning `null` from methods that can reasonably return an empty collection or `Optional<T>` for absent values when it improves clarity. Do not introduce `Optional` in public APIs without a repository-wide decision.
- Naming
  - Packages follow existing structure `it.twinsbrain.dojos`.
  - Classes: PascalCase. Methods & variables: camelCase. Constants: UPPER_SNAKE_CASE.
- Visibility
  - Prefer the narrowest visibility that supports the intended use. Keep helper methods `private` unless used across classes; prefer package-private for tests that need to exercise internal behaviour only when necessary.
- Exceptions & error handling
  - Prefer unchecked exceptions for programming errors. Use checked exceptions only when the caller is expected to recover and the type clarifies the contract.
  - Include helpful messages when throwing exceptions (avoid empty messages).
- Tests
  - Tests live under `src/test/java` mirroring the package of the classes they exercise.
  - Each test should assert a single behavior or a clear small set of related behaviors.
  - Use descriptive test method names (e.g., `shouldAddPlayerWhenNameIsNew`).
  - Tests must be runnable via `./mvnw test` and produce surefire reports.

CI recommendations (optional)
---------------------------
- Minimal GitHub Actions workflow an agent can propose (example summary):
  1. Checkout repository
  2. Run `./mvnw -B -DskipTests=false test`
  3. Publish `target/surefire-reports/` as artifact and fail build on test failures.
- If adding linters/formatters to CI, gate them behind a separate job and ensure the `pom.xml` contains the required plugin configuration.

Verification steps an agent should run after making changes
---------------------------------------------------------
1. Run `./mvnw -q test` to ensure tests pass.
2. Run a single test command to verify targeting works: `./mvnw -Dtest=MineGooseGameTest#testMethodName test`.
3. Inspect `target/surefire-reports/` for the generated reports.

Escalation & change policy
--------------------------
- Do not add or change project-wide formatter/linter configurations (files in repo root or `pom.xml`) without explicit approval from a human maintainer.
- If tests fail after your change, report failing tests, stack traces, and surefire output to the maintainer.
